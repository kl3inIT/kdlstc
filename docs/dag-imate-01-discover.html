DAG này chỉ trả lời một câu — “nguồn có gì mới?” — nhưng mỗi quyết định bên trong đều nhằm một kiểu hỏng cụ thể đã đo được trên API thật. Trang này vẽ cơ chế và ghi rõ vì sao làm thế ngay cạnh từng chỗ.

1 · Một lượt chạy — ai đứng đâu, vì sao có cái pod

Worker Airflow mang IP 10.42.x.x — dải này bị firewall lọc ở cổng 80 (đo thật: cổng 6443 cùng máy chủ vẫn thông). Pod gắn hostNetwork mượn IP của node nên đi lọt. Đặc quyền đó được nhốt vào đúng một pod sống vài chục giây, không cấp cho worker chạy mọi DAG.

4 · Bốn đoạn code gánh toàn bộ độ tin cậy

a — Cái bẫy HTTP 200 · imate_common.api_get

request = urllib.request.Request(API_ADDR + path, headers={"Host": API_HOST}) with urllib.request.urlopen(request, timeout=HTTP_TIMEOUT) as response: payload = json.loads(response.read().decode("utf-8")) if not payload.get("success"): # API trả lỗi bằng HTTP 200! raise SourceRefusedError(...)
Vì sao: đo thật — pageSize=101 trả HTTP 200 kèm success:false, body:null. Ai tin status code sẽ đọc lỗi thành “hôm nay không có gì” và pipeline im lặng nạp rỗng. Kiểm cờ ở một chỗ duy nhất, mọi lời gọi hưởng chung. Header Host vì DNS cluster không phân giải imate.local — gọi bằng IP, server chọn app theo vhost.

b — Trí nhớ + phân loại · imate_fetch.discover

known = {gid: ts.isoformat().replace("+00:00", "Z") for gid, ts in cur.fetchall()} ... previous = known.get(row["globalId"]) if previous is None: page_fresh += 1 # MỚI elif previous != row["updatedAt"]: page_changed += 1 # ĐÃ SỬA else: continue # đã biết — không đụng DB
Vì sao: nạp 6.141 cặp (id, updatedAt) vào dict (~1 MB) để so O(1) thay vì 6.141 câu SQL. Chỗ .replace("+00:00","Z") là điểm mong manh có chủ đích ghi chú: đây là so chuỗi — Postgres trả +00:00, API trả Z, lệch định dạng là mọi thứ trông như “đã sửa” và lượt nào cũng thành full scan. Nếu nó hỏng, cầu chì MAX_PAGES ở dưới đỡ.

c — Câu SQL đắt giá nhất · upsert vào worklist

INSERT INTO ingestion.doc_worklist (...) VALUES %s ON CONFLICT (global_id) DO UPDATE SET ..., status = 'discovered', -- bản sửa quay về ĐẦU pipeline last_error = NULL, updated_at = now()
Vì sao: một câu vừa thêm vừa đè — chạy lại lần nữa vô hại (idempotent). Dòng status='discovered' là lý do văn bản đã publish rồi vẫn được cập nhật khi nguồn sửa nó: thiếu dòng này, bản sửa không bao giờ được tải lại và không ai biết. Ghi commit theo trang — chết ở trang 40 thì 39 trang trước còn nguyên, chạy lại là tiếp.

d — Báo cáo qua sổ cái, không qua XCom

cur.execute("UPDATE ingestion.runs SET row_count = %s, message = %s WHERE run_id = %s", (fresh + changed, json.dumps(summary), run_id))
Vì sao: pod muốn đẩy XCom phải có sidecar + volume chung. Mà kết quả đằng nào cũng phải nằm trong sổ cái để truy vết — cho đi hai đường là tạo hai chỗ có thể mâu thuẫn nhau về việc lượt này đã làm gì. close_run chỉ đọc vé rồi quyết.
