Học Airflow qua thực hành

Trang này đi kèm 3 file DAG trong thư mục dags/. Đọc khái niệm → chạy trên server → quan sát → sửa và chạy lại.

01Airflow là gì

Apache Airflow là nền tảng điều phối (orchestration) workflow: bạn khai báo pipeline bằng code Python, Airflow lo lịch chạy, thứ tự, thử lại khi lỗi, và cho bạn UI để theo dõi.

Trong dự án kho dữ liệu, Airflow là "nhạc trưởng" điều phối các bước lấy dữ liệu từ nguồn → biến đổi → nạp vào kho theo lịch, đảm bảo chạy đúng thứ tự và có thể chạy lại an toàn.

Airflow KHÔNG phải là nơi xử lý dữ liệu lớn (không phải Spark). Nó ra lệnh cho các hệ thống khác chạy, rồi theo dõi kết quả. Việc nặng nên đẩy xuống DB/Spark/warehouse.

02Kiến trúc & luồng chạy một task

Bản deploy của bạn dùng CeleryExecutor — task được đẩy qua hàng đợi Redis cho các worker chạy song song:

DAG file.py trong dags/
→
DAG Processorparse file thành DAG
→
Schedulerchọn task tới lượt
→
Redishàng đợi
→
Workerchạy task thật

↑ Trạng thái mọi task + XCom được lưu vào PostgreSQL (metadata DB). Triggerer lo các task chờ (deferrable). API server phục vụ UI.

03Khái niệm cốt lõi

Khái niệmÝ nghĩa
DAGMột pipeline = đồ thị task có hướng, không vòng lặp. Khai báo bằng @dag.
TaskMột bước công việc trong DAG. Khai báo bằng @task hoặc một Operator.
OperatorKhuôn mẫu task dựng sẵn: BashOperator, PythonOperator, EmptyOperator, PostgresOperator…
ExecutorCách chạy task. Bạn dùng CeleryExecutor → task chạy trên worker qua Redis.
Scheduler"Bộ não": đọc lịch, biết task nào đủ điều kiện, phát cho worker.
XComKênh truyền dữ liệu nhỏ giữa task. Với TaskFlow, return tự đi qua XCom.
scheduleLịch chạy: cron ("@daily"), timedelta, None (chỉ chạy tay), hoặc Asset.
logical date"Thời điểm dữ liệu" của lần chạy ({{ ds }}) — khác thời điểm chạy thực. Gốc của tính idempotent.
catchupCó chạy bù các kỳ quá khứ không. Airflow 3.x mặc định False.
Lưu ý phiên bản 3.x: import từ airflow.sdk (không phải airflow.models/airflow.decorators như tài liệu 2.x cũ), và các operator chuẩn nằm trong provider apache-airflow-providers-standard. Nhiều hướng dẫn trên mạng vẫn theo 2.x — sẽ báo lỗi import trên hệ của bạn.

04Bài 1 — Hello Airflow

Mục tiêu: thấy DAG lên UI, unpause, trigger, đọc log; hiểu DAG → Task → Operator và toán tử phụ thuộc >>.

dags/bai01_hello_airflow.py
from __future__ import annotations
from datetime import datetime

from airflow.sdk import dag, task
from airflow.providers.standard.operators.bash import BashOperator


@dag(
    dag_id="bai01_hello_airflow",
    start_date=datetime(2026, 1, 1),
    schedule="@daily",   # cron rút gọn. Đổi thành None để chỉ chạy tay.
    catchup=False,       # 3.x mặc định False -> không chạy bù quá khứ.
    tags=["hoc-airflow"],
)
def hello_airflow():
    # Task Bash: chạy 1 lệnh shell trong worker. {{ ds }} = logical date.
    say_hello = BashOperator(
        task_id="say_hello",
        bash_command="echo 'Xin chao — logical date = {{ ds }}'",
    )

    @task
    def print_context():
        print("Task Python dang chay trong worker.")
        return 42   # giá trị này được lưu vào XCom

    # say_hello chạy XONG rồi mới tới print_context
    say_hello >> print_context()


hello_airflow()   # gọi ở top-level để Airflow đăng ký DAG
Quan sát: Vào Grid → click ô say_hello → Logs xem dòng echo. Sau đó thử đổi schedule="@daily" thành None, lưu, và xem DAG không còn tự lên lịch nữa.

05Bài 2 — TaskFlow API & truyền dữ liệu (XCom)

Mục tiêu: mô hình extract → transform → load; giá trị return tự đi qua XCom sang task sau, không cần xcom_pull() thủ công. Đây là "hình dạng" của gần như mọi pipeline kho dữ liệu.

dags/bai02_taskflow_etl.py
from __future__ import annotations
from datetime import datetime
from airflow.sdk import dag, task


@dag(
    dag_id="bai02_taskflow_etl",
    start_date=datetime(2026, 1, 1),
    schedule=None,   # chỉ chạy khi bấm Trigger
    catchup=False,
    tags=["hoc-airflow"],
)
def taskflow_etl():
    @task
    def extract() -> dict:
        # Giả lập lấy dữ liệu nguồn. Sau này thay bằng API/DB thật.
        return {"HD001": 301.27, "HD002": 433.21, "HD003": 502.22}

    @task
    def transform(orders: dict) -> dict:
        total = sum(orders.values())
        return {"tong_gia_tri": round(total, 2), "so_hoa_don": len(orders)}

    @task
    def load(summary: dict) -> None:
        # Sau này: ghi vào bảng warehouse. Giờ in ra log.
        print(f"Nap vao kho: {summary}")

    # output hàm này là input hàm kia -> Airflow tự suy ra thứ tự
    load(transform(extract()))


taskflow_etl()
Quan sát: Sau khi trigger, click task transform → tab XCom để thấy dữ liệu {tong_gia_tri, so_hoa_don} được truyền sang load.

06Bài 3 — Phụ thuộc, Retry & Rẽ nhánh

Mục tiêu: default_args để retry; @task.branch để rẽ nhánh theo điều kiện; trigger_rule để gộp nhánh. Nền cho pipeline thật: có dữ liệu thì xử lý, không thì bỏ qua, lỗi tạm thời thì tự thử lại.

dags/bai03_dependencies_retries.py
from __future__ import annotations
from datetime import datetime, timedelta

from airflow.sdk import dag, task
from airflow.providers.standard.operators.empty import EmptyOperator


@dag(
    dag_id="bai03_dependencies_retries",
    start_date=datetime(2026, 1, 1),
    schedule=None, catchup=False,
    default_args={
        "retries": 2,                        # thử lại tối đa 2 lần khi fail
        "retry_delay": timedelta(seconds=30),
    },
    tags=["hoc-airflow"],
)
def dependencies_retries():
    start = EmptyOperator(task_id="start")

    @task
    def check_source() -> int:
        return 120   # đổi thành 0 để thử nhánh còn lại

    @task.branch
    def route(count: int) -> str:
        # trả về task_id của nhánh SẼ chạy; nhánh kia bị skip
        return "process_data" if count > 0 else "skip_empty"

    @task
    def process_data() -> None:
        print("Co du lieu -> xu ly")

    skip_empty = EmptyOperator(task_id="skip_empty")
    join = EmptyOperator(
        task_id="join",
        trigger_rule="none_failed_min_one_success",  # chạy dù nhánh nào thắng
    )

    count = check_source()
    start >> count
    route(count) >> [process_data(), skip_empty] >> join


dependencies_retries()
Quan sát: Trigger với return 120 → nhánh skip_empty có màu hồng "skipped". Sửa thành return 0, trigger lại → đảo nhánh, nhưng join vẫn chạy nhờ trigger_rule.

07Đưa DAG lên server & chạy

Chuẩn bị kết nối tới môi trường triển khai. Dùng hostname do quản trị viên cấp.

1) Đẩy file DAG lên server

từ máy local (PowerShell)
scp dags/*.py airflow-host:/opt/airflow/dags/

airflow-host là alias SSH ví dụ trong ~/.ssh/config; thay bằng hostname của môi trường.

2) Mở UI và chạy

  1. Mở địa chỉ Airflow do quản trị viên môi trường cung cấp.
  2. Chờ ~30s–5 phút để DAG Processor quét file mới — không cần restart.
  3. Gạt nút Unpause (DAG mới mặc định bị pause).
  4. Bấm Trigger DAG → vào Grid / Graph xem task đổi màu → click ô task → Logs.

Xử lý nhanh nếu DAG không hiện

trên server
ssh kdlstc-dev
cd /home/ubuntu/app/airflow
docker compose ps                          # tất cả phải healthy
docker compose exec scheduler airflow dags list   # DAG đã được parse chưa
docker compose logs dag-processor --tail=50       # lỗi cú pháp sẽ hiện ở đây

08Lộ trình tiếp theo (bám dự án kho dữ liệu)

4 · Connections & Hooks

Kết nối PostgreSQL thật, ghi vào bảng warehouse. Bài đầu tiên "chạm" kho dữ liệu.

5 · Sensors

Chờ file/nguồn sẵn sàng rồi mới ingest, thay vì chạy mù theo giờ.

6 · Idempotency & Backfill

Chạy lại một ngày không nhân đôi dữ liệu ({{ ds }} + DELETE/MERGE). Cốt lõi cho milestone reconciliation.

7 · Dynamic Task Mapping

Một DAG ingest N nguồn / N bảng song song mà không lặp code.

8 · Assets (Datasets)

DAG B tự chạy khi DAG A cập nhật xong dữ liệu — pipeline hướng dữ liệu.

9 · Alerting & SLA

Cảnh báo khi pipeline fail/chậm; retention log; backup metadata DB.
